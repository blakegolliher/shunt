# ADR-0017: a web UI over the control API

Status: accepted (UI-6, 2026-09-22). UI-0 through UI-6 are built and their Go, UI-unit, fleet and license gates pass; browser-flow and screenshot acceptance are manual by the operator's explicit choice. Overrides the "a web UI" entry of docs/DESIGN.md §3 (non-goals for v1) on the `distributed` branch. Supersedes item 1 of docs/prompts/P3e.md. Source: docs/prompts/webui.md.

## Context

Every operator action is a CLI verb over the control API (ADR-0008). A demo that walks a bucket across clusters (docs/prompts/webui.md, the demo table) needs the same actions from a browser, with what the CLI prints as text shown live: the two-phase fence pending then applied, the write split, fallback reads trending to zero, the purge dry run. The API as it stood could not carry that: each long-running verb was one blocking HTTP call whose fence state (waiting-on names) was discarded when it answered; members long-polled a payload that carries secrets; `GET /v1/status` mixed every read model; `purge-source` and `cluster remove` had no dry run.

## Decision

### The stack (built from UI-2)

- **Vite + React + TypeScript + Tailwind CSS; Recharts for graphs.** All MIT. Copyright notices are preserved; `web/THIRD_PARTY_NOTICES` is generated from `package.json` at build and merged into the repo's `THIRD_PARTY_NOTICES` by `make licenses`; docs/deps.md lists each production dependency with one line on why the stdlib was not enough, as for Go modules.
- **Delivery.** `make ui` builds `web/dist`; `shunt-control` embeds it with `embed.FS` and serves it on the control API port at `/`. Node is a build-time dependency only. A committed stub `web/dist/index.html` ("UI not built, run make ui") keeps `go build` working without Node; `web/dist` is otherwise gitignored; CI runs `make ui` before `make build`. Still two binaries.
- **Auth for the demo.** The bearer token is pasted once, held in `sessionStorage`, and sent as `Authorization: Bearer`. OIDC with roles is the P3c amendment's later item; the API surface does not change when it lands. Until then the token is admin-equivalent, as it is for the CLI.
- **Percentiles are emitted, never computed in the browser.** Proxies keep HdrHistogram sketches (`github.com/HdrHistogram/hdrhistogram-go`, MIT) per 10 s window and ship them compressed in heartbeats; control nodes merge them and serve p50/p90/p99/p99.9. Fleet, cluster and proxy views are merges of the same sketches, never averages of percentiles (UI-1).
- **The browser mover is a control-node worker, never a proxy request.** `POST /v1/operations` with kind `mover` invokes the same `internal/mover` engine as `shunt migrate run`; it resolves the control plane's sealed cluster secrets, writes a local cursor and append-only ledger below that node's data directory, and reports bucket-level counts to the existing in-memory convergence read model. Its operation record is fleet-visible, but cursor, ledger and convergence remain owned by the node doing the work. If that node fails, the record fails and an operator repeats the idempotent guarded mover on another node. `GET /v1/placements/{tenant}/{bucket}/mover-ledger` exposes only a bounded ledger tail. No per-object record enters etcd or the directory.
- **Theme.** Burnt orange on black. Tailwind palette: `ember-500 #CC5500` (primary), `ember-400 #E06A1F`, `ember-600 #A64400`, `ember-300 #F08A4B`; `ink-950 #0B0B0B` (background), `ink-900 #141414`, `ink-800 #1F1F1F`, `ink-700 #2A2A2A`; text `#F2ECE6`; muted `#9A928B`. Destructive actions use `red-600`, not orange, so purge never looks like a normal button. Contrast for all text is at least 4.5:1, checked by a test.

### The API (built in UI-0)

- **Operation records.** Every long-running action (a ramp step, migrate start, cutover, purge-source, migrate finish, cluster remove) runs under a record: id, kind, placement or cluster, actor, owning node, status (`running | succeeded | failed | refused`), phase (`queued | precondition | hold | step | settle | window | diff | purge | done`), the proxies it is waiting on, progress where there is any, the result or the error. `POST /v1/operations` starts one and answers 202 at once; `GET /v1/operations/{id}` and `GET /v1/operations?placement=` read them. The existing routes stay for the CLI and the walkthrough: each now runs the same code under a record and answers as before plus the record's id. The CLI's `--wait` polls the record. The server-side `wait` keeps the fence semantics of ADR-0016 exactly: a hold that does not reach every member within it is released.
- **Records live behind a seam, `control.Operations`, with two real implementations**, named here beside `Fleet` and `Keys` (ADR-0015) for the same reason: the etcd client must not link into `bin/shunt`. `control.MemOperations` serves the lab proxy and tests (a ring of 1 000 in insertion order); `cp.Operations` keeps them in etcd under `/shunt/ops/<id>`, outside `/shunt/v1/` so the directory version never moves for a record, with a retention of 1 000 and one watch on the prefix that fans every update to every node. Ids are time-sortable (`<unix-ms>-<6 hex>`). A record is per operation, never per object (CLAUDE.md). A record is owned by the node that runs it; a node marks its own `running` records failed ("control node restarted") once it has quorum again. A held step left by such a restart still completes by repeating it (ADR-0016).
- **Operations run on the server's context, never the request's.** A client that leaves, or a CLI killed while it waits, does not stop a fenced step halfway; the record has its outcome, and the CLI's `--wait` running out leaves the operation running and prints the id to follow.
- **`GET /v1/events`** is server-sent events from the control node: `directory` (a record changed, with the record and the version), `fence` (an operation's phase, status and waiting-on names), `fleet` (a proxy joined, left, fell silent, came back, or applied a version), and `telemetry` (reserved for UI-1). Ids are `<node-epoch>:<seq>` from a per-node ring of 4 096 events. A `Last-Event-ID` inside the ring replays what was missed; any other id (another node, a restart, too old) gets a `reset` event first and the client reloads its read models. The bearer token is the only authentication, so the browser reads the stream with `fetch` and the `Authorization` header (`EventSource` cannot send headers); a token never goes in a URL. `fence` events reach every node through the operations watch, so a UI on one node sees an operation another node runs.
- **Read models carry no secret.** `GET /v1/clusters/{name}/view`, `GET /v1/placements/{tenant}/{bucket}/view` and `GET /v1/audit` are built for the browser. `GET /v1/placements/{tenant}/{bucket}` keeps its secrets for the mover. Fleet members report `host` and `version` in their heartbeat; a member that is not `live` is what the UI shows as stale. Audit is the change records both backends already write, read back for the first time (`Store.Changes`).
- **Dry run and confirmation in the API, not the client.** `purge-source` with `dry_run: true` and `DELETE /v1/clusters/{name}?dry_run=1` answer what would happen (`allowed`, the refusal reason if not, the counts, the references) and a confirmation token; the real call must present it. Tokens are stateless: HMAC-SHA256 over the operation's scope, a digest of the records the action depends on, and the issue time, valid for 10 minutes, keyed by `Server.ConfirmKey`. `shunt-control` derives the key from the data-encryption key, so any node verifies a token any node issued; the lab proxy uses 32 random bytes per process. Purge binds to the placement and the source cluster definition, **not** to object counts: deletes still reach the source in CUTOVER, so counts drift under client traffic and are shown as information. The CLI runs the dry run, prints the summary, and proceeds with the token; `--dry-run` stops after the summary.
- **`GET /v1/control`** is `GET /v1/control/status` under its own name, extended with `last_compaction` (etcd's own gauge, null until a compaction has run since start) and a `join` line for a new node built from the flags this node runs with.
- **The route table is code.** `Handler()` is built from `control.Routes()`, each route naming the CLI verbs that reach it; a test keeps `docs/reference/control-routes.json` equal to it, for UI-2's parity test.
- **Upgrade order: control nodes before proxies.** A heartbeat is decoded with unknown fields refused, so a new proxy sending `host` and `version` to an old node is refused until the node is upgraded.
- CORS is not enabled: the UI is same-origin on the control port. No new Go dependency and no new metric in UI-0.

### Alternatives rejected

- **Records in the running node's memory only.** A UI attached to another control node, or the CLI behind a load balancer, would not see them, and a restart would lose a running record's outcome. Mover progress is still per node (it re-reports on its next pass); records are not.
- **The token in the SSE URL** (`?token=`), which is what `EventSource` would need. URLs land in logs and history; `fetch` streaming costs the browser client twenty lines.
- **Averaging percentiles** across proxies: an average of p99s is not a p99. Sketches merge; that is why the proxies ship them (UI-1).
- **A separate `GET /v1/control` route beside `/v1/control/status`** with its own struct: one handler, two patterns, one struct keeps the CLI's `status` the UI's twin.
- **Go templates and htmx** (docs/prompts/P3e.md item 1): no build step, but every live element becomes a server round trip and a chart library would still be vendored. The UI is a client of the API, and a client stack is the ordinary way to build one; Node stays out of the runtime.

## Consequences

- New surface: `POST /v1/operations`, `GET /v1/operations[/{id}]`, `GET /v1/events`, `GET /v1/clusters/{name}/view`, `GET /v1/placements/{tenant}/{bucket}/view`, `GET /v1/audit`, `GET /v1/control`, `dry_run` on `purge-source` and `DELETE /v1/clusters/{name}`, the `operation` field on transition results, `host` and `version` on fleet members, `docs/reference/control-routes.json`; CLI `purge-source --wait --dry-run`, `cluster remove --dry-run`; `Store.Changes` on the directory seam.
- The `Operations` seam has two implementations that are not test doubles, as `Fleet` and `Keys` do; the lab proxy's is the memory one.
- Every mutating verb's refusal text is unchanged; `make fleet` asserts on it.
- The browser stack, the embedding, and the UI's own tests come with UI-2 to UI-6, each recorded against this ADR.
