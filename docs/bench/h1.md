# H1 benchmarks: data path unchanged, installs pay for a durable cache

H1 (ADR-0021 D1: H1a–H1e) left the data path's benchmarks statistically unchanged. A request now
acquires and releases a counted runtime bundle; that costs 37 ns with sixteen goroutines on one
bundle, and `ResignSmallGET` does not move. The one real slowdown is a member's install, which
now writes a checksummed cache and syncs its directory: +2.4 ms (+20 %) for 1,000 placements, off
the request path and after the install lock is let go. Measured 2026-09-24.

## Method

- Host: AMD EPYC 7402P (24 cores, 16 visible), Linux 5.14.0-570.17.1.el9_6.x86_64, Go 1.27.1,
  `GOMAXPROCS` 16. Both sides ran on the same host, one after the other, with no demo fleet or
  other shunt process running (the e2e MinIO and Garage containers were up and idle).
- Before: commit `64148e8` (docs: H0 passed), the last commit before H1a, in a separate worktree.
  After: `0287048` (H1e) plus the H1f working tree, which adds tests and benchmarks only.
- `go test -run '^$' -bench . -benchmem -benchtime 1s -count 6` over the request-path packages:
  `internal/proxy`, `internal/sigv4/...`, `internal/s3/...`, `internal/upstream`,
  `internal/migrate`, `internal/directory`. Compared with benchstat at the Makefile's pinned
  version.
- Raw output: `test/bench/h1/datapath-64148e8.txt`, `test/bench/h1/datapath-h1.txt`, and the
  comparison `test/bench/h1/datapath-benchstat.txt`; the install comparison in
  `test/bench/h1/install-*.txt`; the control-plane set in `test/bench/h1/control-plane-h1.txt`.

## Data path: before and after

No benchmark got significantly slower (p < 0.05). Three got significantly faster, all in code H1
did not touch, so they are run-to-run noise: `directory.Create` −11.9 % (p=0.002),
`sigv4.Sign` −8.7 % (p=0.041) and `proxy.SpreadListingPage/legs=8` −5.0 % (p=0.041). Allocations
and bytes are unchanged on every row, including the two resign-mode request benchmarks that now
acquire and release a bundle:

| Benchmark | Before | After | Change |
|---|---|---|---|
| `proxy.ResignSmallGET` | 522.2 µs ± 16 %, 240 allocs | 495.4 µs ± 11 %, 240 allocs | ~ (p=0.485) |
| `proxy.ResignSignedChunkPUT1MiB` | 4.99 ms ± 22 %, 4,728 allocs | 5.17 ms ± 7 %, 4,727 allocs | ~ (p=0.818) |
| `upstream.RegistryLoadGet` | 13.6 ns, 0 allocs | 14.8 ns, 0 allocs | ~ (p=0.818) |

## Member install: +20 %, the durable cache

`member.Install` (one directory version of 1,000 placements: validate, publish, cache write),
before and after on the same quiet host:

| | Before | After | Change |
|---|---|---|---|
| time | 12.08 ms ± 5 % | 14.49 ms ± 8 % | +20.0 % (p=0.002) |
| memory | 2.263 MiB | 2.358 MiB | +4.2 % (p=0.002) |
| allocs | 18.10 k | 18.11 k | ~ |

With the parent-directory fsync switched off (an experiment, not committed) the same benchmark
takes 13.76 ms (+13.9 %), so that sync costs about 0.7 ms. The remaining ~1.7 ms is the envelope:
the directory is marshalled once, checksummed with SHA-256, and passed through the envelope's
encoder, which compacts the embedded directory in a second pass. That buys a cache that a crash
cannot tear and a copy from another proxy cannot pass for this one's (H1d, T04). The cache write
now runs after the install lock is let go, so the next install does not wait behind the disk.

## Control plane after H1

`go test -run '^$' -bench '<names>' -benchmem -benchtime 1s -count 6` over `internal/member`,
`internal/upstream` and `internal/runtimecfg`. Medians of six runs.

| Benchmark | What it is | Time | Memory | Allocs |
|---|---|---|---|---|
| `runtimecfg.Load` | a status read of the published bundle | 0.12 ns | 0 B | 0 |
| `runtimecfg.Acquire` | a request acquiring and releasing its bundle, 16 goroutines on one bundle | 37.0 ns ± 1 % | 0 B | 0 |
| `runtimecfg.Publish` | one install's publication, the old bundle drained at once | 1.59 µs ± 33 % | 936 B | 17 |
| `runtimecfg.PublishBackpressured` | one publication while eight retired bundles are held: it replaces the pending bundle | 1.66 µs ± 23 % | 936 B | 17 |
| `member.CacheWrite` | one durable cache write: marshal, checksum, write, fsync, rename, directory fsync | 4.62 ms ± 7 % | 1.98 KiB | 22 |
| `member.Install` | 1,000 placements, as above | 16.9 ms ± 25 % | 2.30 MiB | 18.1 k |
| `member.Install100k` | design §8's snapshot reload: one version of 100,000 placements | 854 ms ± 11 % | 224 MiB | 1.65 M |
| `member.StaleParallel` | the lease check for moving buckets, 16 goroutines | 4.1 ns ± 10 % | 0 B | 0 |
| `upstream.RegistryLoadGet` | a request loading the cluster set | 15.3 ns ± 21 % | 0 B | 0 |

`member.Install` reads 16.9 ms in this run and 14.5 ms in the paired comparison above; the
control-plane set ran right after the data path, and its ±25 % spread covers both.

Design §8's snapshot-reload row asks for three bounds on a 100,000-placement reload, and each is
met by construction and covered by a test:

- **One installation build per version.** Installs are serialized under the member's install lock.
  An older or duplicate version is dropped before it is built (`TestMemberNeverInstallsAnOlderVersionOverANewerOne`).
- **One coalesced cache write.** The write runs outside the lock, serialized, and skips any version
  older than one already written (`TestMemberNeverInstallsAnOlderVersionOverANewerOne` checks the cache stays at the newest; `TestCacheFaults` covers each failing stage).
- **At most eight retained bundles.** Past eight, installs coalesce into one pending bundle
  (`TestRetiredBound`, `TestInstallBackpressure`).
- **Oversized input refused before it is decoded.** A directory from the control plane or the
  cache is read through a 64 MiB limit first (`TestCacheRejects`, "oversized").

A 100,000-placement version is 224 MiB of transient allocation per install. That is the cost of
decoding, validating and indexing the snapshot, and the snapshot itself stays much smaller.

## Transport reuse, measured on the wire

`TestRotationReusesConnections` (`internal/proxy`) runs fifty secret-only rotations, each published
and followed by a signed request through the proxy, and counts the TCP connections the backend
accepts. The result is one connection. Its negative control changes the endpoint on every rotation,
which builds a new transport each time, and counts fifty. The retired transports' idle connections
close when their last set is released (`TestPoolLifetime`).
